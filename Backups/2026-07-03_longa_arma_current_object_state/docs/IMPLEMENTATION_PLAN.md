# Bellerophon Implementation Plan

이 문서는 `spce.txt` 기획을 실제 Unity 프로젝트에 구현하기 위한 단계별 계획서다. 당장 기능을 구현하지 않고, 하네스 엔지니어링 구조 안에서 어떤 순서와 경계로 구현할지 정한다.

## 1. 구현 기준

### 게임 방향

Bellerophon은 1인칭 3D 우주 화물 운송 협동 생존/공포 게임이다.

플레이어의 핵심 목표는 행성에서 의뢰 또는 개인 화물을 준비하고, 화물선을 운행해 목적지까지 최대한 손실 없이 도착한 뒤, 정산을 통해 돈과 평판을 관리하는 것이다. 게임 오버 조건은 배상/수리/보험 비용을 지불할 돈이 없는 상태다.

Lethal Company는 그래픽 질감, 조명, 폐쇄 공간 분위기, 협동 중 긴장감의 레퍼런스로만 사용한다. 탐사/회수, 할당량, 폐건물 스캐빈징 루프를 핵심 게임 구조로 채택하지 않는다.

### 하네스 제약

- 런타임 게임 로직은 `Assets/_Project/Runtime` 아래 둔다.
- 에디터 자동화와 검증 코드는 `Assets/_Project/Editor` 아래 둔다.
- 순수 규칙, 수치, 정산, 상태 변화는 EditMode 테스트로 먼저 고정한다.
- 씬, 입력, 물리, UI, 상호작용은 PlayMode 테스트로 검증한다.
- Steam, 저장, 업적, 클라우드 같은 외부 기능은 인터페이스 뒤에 둔다.
- 생성물 폴더와 Unity 자동 생성 프로젝트 파일은 관리 대상에서 제외한다.

## 2. 시스템 분해

### 핵심 루프

1. 행성 도착 상태에서 시작한다.
2. 정비소에서 화물선 수리, 업그레이드, 장비 배치를 한다.
3. 의뢰소에서 협회/개인/특수 의뢰 중 운송할 화물을 선택한다.
4. 상점에서 장비, 소모품, 무기, 방호복을 구매하거나 개인 화물을 판매한다.
5. 화물선 운행을 시작한다.
6. 운행 중 플레이어는 조종, 포탑, 통제실, 동력실, 수리, 전투 역할을 나눠 수행한다.
7. 외부 위험 상황과 침입자가 화물선, 화물, 선원을 위협한다.
8. 목적지 행성에 도착하면 의뢰 성공/실패와 비용을 정산한다.
9. 돈, 유명세, 협회 상태, 업그레이드 상태를 저장하고 다음 운송을 준비한다.
10. 정산 후 지불 불능이면 게임 오버다.

### 주요 도메인

- Player: 체력, 보호막, 이동, 아이템 슬롯, 상태이상
- Ship: 6개 구역, 복도, 구역 내구도, 구역 기능, 방별 패널티
- Cargo: 운송 화물, 개인 화물, 등급, 내구도, 크기, 목적지, 판매 보정
- Contract: 협회 의뢰, 개인 의뢰, 특수 의뢰, 난이도, 보상, 필요 창고 점수
- Planet: 행성 특성, 정비소, 의뢰소, 상점, 개인 화물 수집소
- Travel: 운송 시간, 진행도, 자동/수동 운행, 외부 위험 상황
- Threat: 씨앗체, 외계 생명체, 화물 자유 연대, 해적, 침입선
- Combat: 무기, 방호, 피해 계산, 상태이상, 피아식별
- Economy: 정산, 보험료, 수리비, 견인비, 협회 유지비, 유명세
- Progression: 업그레이드, 특수 임무, 해금, 저장 데이터

## 3. 코드 구조 계획

### Runtime 폴더

```text
Assets/_Project/Runtime/
  Core/
    FixedStepAccumulator.cs
    Result.cs
  Game/
    Cargo/
    Combat/
    Contracts/
    Economy/
    Items/
    Planets/
    Player/
    Progression/
    Ship/
    StatusEffects/
    Threats/
    Travel/
  Presentation/
    Cameras/
    Interaction/
    PlayerController/
    ShipStations/
    UI/
  Platform/
```

`Game` 아래 코드는 가능한 한 UnityEngine 의존을 줄인다. 수치 계산과 상태 전이는 plain C#로 작성하고 EditMode 테스트에서 직접 검증한다.

`Presentation` 아래 코드는 MonoBehaviour, Input System, Animator, UI, 씬 오브젝트 연결을 담당한다. 이 계층은 `Game` 규칙을 호출하는 어댑터로 유지한다.

### Editor 폴더

```text
Assets/_Project/Editor/
  Build/
  Validation/
  Authoring/
```

`Authoring`은 이후 ScriptableObject 데이터 검증, 행성/아이템/적대 개체 데이터 검사 도구를 둘 때 사용한다.

### Tests 폴더

```text
Assets/_Project/Tests/
  EditMode/
    Ship/
    Cargo/
    Contracts/
    Economy/
    Combat/
    StatusEffects/
    Threats/
  PlayMode/
    Scenes/
    Interaction/
    ShipStations/
    UI/
```

EditMode 테스트는 빠르고 결정적이어야 한다. 랜덤 위험 상황은 seed를 주입할 수 있게 설계한다.

## 4. 단계별 구현 계획

### Phase 0. 문서 정합성 정리

목표: 프로젝트 문서가 실제 기획과 모순되지 않게 만든다.

작업:
- `docs/GAME_DESIGN.md`를 1인칭 우주 화물 운송 협동 생존/공포 방향으로 갱신한다.
- `docs/DECISIONS/0002-game-direction.md`를 추가한다.
- `docs/SYSTEMS.md`를 추가해 기획을 시스템별로 요약한다.
- `docs/IMPLEMENTATION_PLAN.md`를 유지 관리 기준 문서로 둔다.

완료 기준:
- Lethal Company가 탐사/회수 루프가 아니라 분위기 레퍼런스라는 점이 문서에 명시된다.
- 핵심 루프가 행성 준비, 운송, 위험 대응, 정산으로 정의된다.
- `Run-HarnessValidation.ps1`이 통과한다.

### Phase 1. 순수 도메인 모델

목표: Unity 씬 없이도 게임의 핵심 수치와 상태를 검증할 수 있게 한다.

구현 대상:
- `ShipRoomId`: Cockpit, CargoHold, Armory, SupplyRoom, EngineRoom, ControlRoom
- `ShipRoomState`: 현재 내구도, 최대 내구도, 기능 off 여부, 암전 여부, 폐쇄 여부
- `ShipState`: 6개 구역과 전체 운행 상태
- `CargoGrade`: Common, Rare, Premium
- `CargoState`: 크기, 가치, 내구도, 개인/의뢰 화물 여부
- `ContractType`: Association, Private, Special
- `ContractDifficulty`: Intro, VeryEasy, Easy, Normal, Hard, VeryHard, Master
- `CrewState`: 생존자 수, 사망자 수
- `WalletState`: 보유금, 부채 가능 여부
- `SettlementInput`, `SettlementResult`

EditMode 테스트:
- 구역 내구도 75/50/25/0% 임계값 판정
- 동력실 0%일 때 견인 처리와 운송 실패 판정
- 운송창고 내구도에 따른 창고 점수 계산
- 협회/개인 의뢰 보상 계산
- 정산 후 보유금이 부족하면 게임 오버 판정
- 행성 특성에 따른 개인 화물 판매 보정

완료 기준:
- Unity 씬 없이 정산 결과와 게임오버를 재현할 수 있다.
- 주요 수치 계산이 MonoBehaviour에 존재하지 않는다.

### Phase 2. 1인칭 플레이어 세로 단면

목표: 화물선 내부를 걸어 다니고 기본 상호작용을 수행하는 playable baseline을 만든다.

구현 대상:
- 1인칭 카메라와 플레이어 이동
- WASD 이동, Shift 달리기, Space 점프, Ctrl 앉기
- F 상호작용
- 좌클릭 사용/공격, 우클릭 홀드 조준 또는 모드 전환
- B 아이템 버리기
- 기본 3칸 손 슬롯
- 체력/보호막 HUD
- 조준선 없음. 단 투척/공격 기준점은 화면 중앙 사용

씬/프리팹:
- `Assets/_Project/Scenes/CargoRunMvp.unity`
- `Assets/_Project/Prefabs/Player/Player.prefab`
- `Assets/_Project/Prefabs/UI/Hud.prefab`

PlayMode 테스트:
- 플레이어가 씬에 스폰된다.
- 입력 없이 1프레임 진행 시 콘솔 에러가 없다.
- 상호작용 가능한 오브젝트 앞에서 F 입력 시 이벤트가 발생한다.

완료 기준:
- 그래픽이 임시여도 플레이어 조작 감각과 상호작용 루프가 동작한다.

### Phase 3. 화물선 Graybox

목표: 6개 방과 복도 구조를 MVP 씬에 배치하고 방별 기능을 연결할 준비를 한다.

구현 대상:
- 조종실, 운송창고, 무기실, 비품실, 동력실, 통제실
- 운송창고 중심 연결 구조
- 비품실-무기실, 조종실-동력실, 조종실-통제실, 동력실-통제실, 통제실-무기실 복도
- 각 구역 명칭 표시
- 구역별 내구도 표시용 debug UI
- 각 구역에 상호작용 지점 배치

구역별 MVP 상호작용:
- 조종실: 운행 시작/정지 토글
- 동력실: 오버클럭 토글
- 통제실: 구역 상태 보기
- 무기실: 포탑 모드 진입 placeholder
- 비품실: 기본 아이템 꺼내기 placeholder
- 운송창고: 화물 상태 확인

PlayMode 테스트:
- 각 구역 상호작용 지점이 씬에 존재한다.
- 플레이어가 적어도 한 구역에서 다른 구역으로 이동 가능하다.
- 구역 상태 UI가 Runtime `ShipState`를 읽는다.

완료 기준:
- 화물선 내부에서 역할 분담이 가능한 공간 구조가 생긴다.

### Phase 4. 운송 루프 MVP

목표: 첫 번째 완전한 게임 루프를 만든다.

MVP 루프:
1. 시작 행성에서 고정 튜토리얼 협회 의뢰를 선택한다.
2. 기본 화물 1개가 운송창고에 적재된다.
3. 출발하면 운행 진행도가 오른다.
4. 운행 중 단순 위험 이벤트가 1회 발생한다.
5. 위험 이벤트는 랜덤 구역 내구도를 감소시킨다.
6. 플레이어는 긴급 수리 장치로 구역을 수리할 수 있다.
7. 운행 시간이 끝나면 목적지 도착으로 처리한다.
8. 정산 화면에서 보상, 수리비, 보험료, 최종 금액을 표시한다.
9. 돈이 부족하면 게임 오버를 표시한다.

처음 넣을 위험:
- 소형 소행성 지대만 구현
- 자동 운행 중 일정 확률로 랜덤 구역 내구도 감소
- 수동 조종/포탑 회피는 placeholder로 두고 Phase 6 이후 확장

EditMode 테스트:
- 운행 시간 진행
- 위험 이벤트 발생 seed 고정
- 구역 피해 적용
- 정산 결과 계산

PlayMode 테스트:
- 운송 시작 버튼을 누르면 진행도가 증가한다.
- 위험 발생 후 구역 내구도 UI가 갱신된다.
- 도착 후 정산 UI가 열린다.

완료 기준:
- 한 판의 시작, 운행, 피해, 도착, 정산, 게임오버 판정이 연결된다.

### Phase 5. 방별 기능 1차 구현

목표: 화물선 관리가 게임의 핵심 플레이가 되게 만든다.

조종실:
- 자동 운행과 수동 운행 상태를 분리한다.
- 조종실 내구도 50% 이하에서 자동 운행 불가를 적용한다.
- 수동 운행 모드는 처음에는 2D 회피 미니게임으로 구현한다.

동력실:
- 오버클럭 1회 제한을 구현한다.
- 오버클럭 중 운행 속도 증가를 적용한다.
- 동력실 내구도 하락 시 암전 구역을 생성한다.

통제실:
- 구역 상태 전개도를 구현한다.
- CCTV는 첫 단계에서 카메라 전환이 아니라 구역 상태/침입자 수 표시로 시작한다.
- 구역 임시 폐쇄와 내부 정화는 데이터 규칙부터 구현한다.

무기실:
- 포탑 수동 모드의 입력과 탄창/장전 규칙을 구현한다.
- 소형 소행성 요격을 먼저 연결한다.

비품실:
- 장비 보관 슬롯을 구현한다.
- 기본 아이템 꺼내기와 반납을 구현한다.

운송창고:
- 화물 내구도와 손실률을 구현한다.
- 운송창고 내구도 25% 이하 출발 불가 규칙을 구현한다.

완료 기준:
- 방별 기능이 단순 UI가 아니라 운송 결과와 정산에 영향을 준다.

### Phase 6. 아이템, 전투, 상태이상

목표: 플레이어가 침입자와 위험에 대응할 수 있게 한다.

MVP 아이템:
- 막대기
- 손전등
- 부상 완화제
- 긴급 수리 장치
- 섬광탄

1차 확장 아이템:
- 머스켓
- 샷건
- 전류봉
- 제압 방패
- 보호막 충전 배터리
- 임시 개방 장치

상태이상:
- 정지
- 화상
- 출혈
- 탈진
- 피로
- 현기증
- 혼란

구현 원칙:
- 무기별 피해, 사거리, 딜레이는 데이터로 둔다.
- 상태이상은 `StatusEffectInstance`로 관리한다.
- 공격 판정은 Presentation 계층, 피해 계산은 Game 계층이 담당한다.

EditMode 테스트:
- 피해와 보호막 우선 차감
- 보호막에 2배 적용되는 폭발 피해
- 상태이상 지속시간과 중첩 규칙
- 아이템 사용 후 쿨타임과 소모 처리

완료 기준:
- 최소 전투 루프가 수치 테스트와 플레이 씬에서 모두 동작한다.

### Phase 7. 침입자와 위험 디렉터

목표: 운행 중 위협이 화물선 내부 협동을 요구하게 만든다.

공통 AI 골격:
- 소속
- 목표 우선순위
- 현재 목표
- 유대/동맹/경쟁/적대 관계
- 방 이동
- 공격
- 특수 행동

구현 순서:
1. 씨앗체 `파르붐`: 금속/구역 내구도 공격
2. 외계 생명체 `칸타빌레`: 소리 목표, 정지 상태이상
3. 화물 자유 연대 `니게티프`: 화물 내구도 탈취
4. 해적 `파후르`: 화염 공격
5. 침입선과 무기실 요격
6. 세력 관계와 개체 간 전투
7. 지휘관형 해적 `아타`

위험 상황 구현 순서:
1. 소형 소행성 지대
2. 대형 소행성 지대
3. 외계 생명체 출몰 구역
4. 화물 자유 연대 출몰 지역
5. 우주 해적 출몰 지역
6. 은폐 블랙홀

검증:
- Threat Director는 seed 기반으로 테스트한다.
- 각 적대 개체는 목표 선택 테스트를 가진다.
- PlayMode에서는 하나의 침입자가 구역으로 이동하고 피해를 주는 smoke test를 둔다.

완료 기준:
- 운행 중 최소 하나의 외부 위험과 하나의 내부 침입자가 실제 손실을 만든다.

### Phase 8. 행성, 상점, 정비, 의뢰

목표: 운행 전 준비와 운행 후 성장 루프를 만든다.

행성:
- 행성 특성 6종을 데이터화한다.
- 행성 특성 중첩 가능 여부를 설정값으로 둔다.
- 개인 화물 판매 보정표를 구현한다.

정비소:
- 구역별 수리비 계산
- 전체 수리
- 구역 내구도 업그레이드
- 무기실, 자동 항법, 비품실, 통제 강화 업그레이드

의뢰소:
- 협회 의뢰, 개인 의뢰, 특수 의뢰 타입 분리
- 난이도별 유명세 변화
- 필요 창고 점수
- 협회 가입 여부에 따른 노출 개수 차이
- 회생 의뢰

상점:
- 구매 탭과 판매 탭
- 공통 상품
- 유명세 제한 상품
- 특수 임무 해금 상품

완료 기준:
- 플레이어가 운행 전 선택으로 운행 리스크와 보상을 바꿀 수 있다.

### Phase 9. 시작 시퀀스와 협회 시스템

목표: 기획의 독특한 협회 계약 경험을 구현한다.

구현 대상:
- 자동 스크롤 계약서
- 아래 방향키 빠른 스크롤
- `예` 버튼 진행
- 일반 입력 차단
- `Ctrl+C` 후 `Ctrl+X`로 계약 중단
- 협회 가입 루트와 개인 사업자 루트 분기
- 히든 업적은 Steam 연동 전에는 플랫폼 인터페이스 Mock으로 처리

주의:
- 이 시퀀스는 UX가 의도적으로 불편한 연출이다. 하지만 실제 입력 잠금이 게임을 종료 불가능하게 만들면 안 된다.
- 개발 빌드에서는 탈출용 debug 입력을 둘지 결정해야 한다.

완료 기준:
- 첫 시작 경험이 게임의 세계관과 경제 구조를 설명한다.

### Phase 10. 저장, 플랫폼, Steam 준비

목표: 진행 상태와 해금을 유지하고 외부 플랫폼 의존성을 격리한다.

인터페이스:
- `ISaveService`
- `IAchievementService`
- `ICloudService`
- `IPlatformUserService`

저장 데이터:
- 보유금
- 화물선 구역 내구도와 업그레이드
- 협회 가입 상태
- 유명세와 협회 유명세
- 해금된 아이템
- 방문한 행성 특성 기록
- 특수 임무 진행도

검증:
- EditMode에서 저장 데이터 직렬화/역직렬화 테스트
- Null/Mock 플랫폼 구현으로 Steam 없이 테스트 가능

완료 기준:
- Steam SDK 없이도 전체 테스트가 실행된다.

### Phase 11. 멀티플레이

목표: 협동 플레이를 추가한다.

전제:
- 싱글 플레이 세로 단면이 안정화된 뒤 시작한다.
- Runtime 규칙이 네트워크 없이 테스트 가능해야 한다.
- 서버 권한 모델을 먼저 결정한다.

동기화 우선순위:
1. 플레이어 위치와 애니메이션
2. 상호작용 소유권
3. 구역 내구도와 화물 상태
4. 운행 진행도와 위험 이벤트
5. 침입자 위치와 행동
6. 정산 결과
7. 저장 데이터

완료 기준:
- 최소 2명이 같은 화물선에서 역할을 나눠 운행을 완료할 수 있다.

## 7. 완료 기준

각 기능은 다음 중 하나 이상의 검증 경로를 가져야 한다.

- 수치/규칙 변경: EditMode 테스트
- 씬/상호작용/UI 변경: PlayMode 테스트
- 패키지/빌드 설정/씬 포함 변경: Windows 개발 빌드
- 하네스 규칙 변경: `docs/HARNESS.md`와 검증 스크립트 갱신

기능 완료 시 최소 실행 순서:

```powershell
.\scripts\Run-HarnessValidation.ps1
.\scripts\Run-EditModeTests.ps1
.\scripts\Run-PlayModeTests.ps1
```

빌드, 씬 목록, 패키지, 프로젝트 설정을 바꾸면 추가로 실행한다.

```powershell
.\scripts\Build-WindowsDev.ps1
```

## 8. 주요 리스크와 대응

- 기획 수치가 많다: 모든 수치를 한 번에 구현하지 않고 MVP 수치 세트와 확장 수치 세트를 분리한다.
- MonoBehaviour에 규칙이 섞일 수 있다: 수치 계산은 `Game` 계층, 씬 연결은 `Presentation` 계층으로 분리한다.
- 적대 개체가 너무 많다: 공통 AI 골격을 먼저 만들고 개체별 특수 행동을 순차 추가한다.
- 멀티플레이가 전체 구조를 흔들 수 있다: 싱글 세로 단면 후 서버 권한 모델을 결정한다.
- 정산 공식이 복잡하다: `SettlementCalculator`를 독립 클래스로 두고 테스트 케이스를 많이 만든다.
- UI가 많은 게임이다: MVP에서는 debug UI와 기능 UI를 분리하고, 최종 연출은 후순위로 둔다.
