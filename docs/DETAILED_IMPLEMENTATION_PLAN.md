# Detailed Implementation Plan

## Implementation Status

- Step 3 completed on 2026-06-05.
  - Contract selection is now separated from planet maintenance through `ContractBoardController`.
  - The maintenance screen only exposes repair, contract board, shop, personal cargo, and upgrade entry points.
  - Contract board category buttons now select categories/rows only; selectable contract rows plus the separate `Accept` button are the only supported acceptance flow.
  - Added reputation state and rules for fame, association fame, success/failure deltas, private contract hiding below low fame, one-time revival contracts, and forced association membership for low-fame non-members.
  - Association maintenance fee constants are shared by detailed contract rules and settlement input construction.
  - Phase10/11/12/14/15/18 open-editor smoke tests were updated to use the maintenance -> contract board -> contract selection flow.
- Step 2 completed on 2026-06-05.
  - Added temporary pure C# catalog data for planets, routes, cargo, and contracts.
  - Distance is modeled as a simple numeric route input because it currently represents transport duration rather than spatial coordinates.
  - Contract reward calculation is traceable as cargo value 60%, route distance 30%, and fame/association fame 10%.
  - Association exposure and acceptance rules are verified in EditMode; contract selection now happens through the separate contract board added in step 3.
- Step 1 completed on 2026-06-05.
- Runtime data types were added as pure C# skeletons first; detailed values and rules stay deferred to the matching later steps.
- PlayMode runner stabilization is tracked in `docs/PLAYMODE_TEST_RUNNER_STABILITY.md`.
- Verified with harness validation, EditMode tests, feature-specific open-editor PlayMode smoke tests, Phase18 MVP smoke, and Windows dev build; the generic open-editor PlayMode Test Runner callback timed out after request pickup during the Step 3 UX correction.

이 문서는 MVP 18단계 완료 이후의 세부 구현 순서를 정리한 검토용 계획서다. `docs/GAME_DESIGN_SOURCE.txt`, `docs/GAME_DESIGN.md`, `docs/MVP_IMPLEMENTATION_ORDER.md`, `docs/PROGRESS_2026-06-02.md`, `docs/PROGRESS_2026-06-05.md`를 기준으로 작성했다.

## 승인 상태

- 상태: 사용자 확인 전 초안
- 원칙: 이 문서가 사용자에게 승인되기 전에는 상세 구현 단계 작업을 시작하지 않는다.
- 범위: 싱글 플레이 및 로컬 협동을 포함한 상세 구현을 먼저 완료한다.
- 온라인/멀티플레이: Steam 로비, 온라인 접속, 최대 5인 동기화 구현은 상세 구현 완료 후 별도 설계와 승인 단계에서 진행한다.

## 현재 기준선

- MVP 18단계까지 구현되어 있다.
- 첫 시작, 협회 계약, 튜토리얼 운송, 자동/수동 운행, 소행성 위험, 수동 포탑, 정산, 정비, 다음 운송, Parvum 침입자, 장비 루프, HUD/맵/분위기, 로컬 협동 상태 경계, 반복 플레이테스트 smoke가 존재한다.
- `IPlatformServices`, `IPlatformMultiplayerServices`, `NullPlatformMultiplayerServices` 경계가 있으나 실제 Steam 또는 온라인 네트워크 기능은 붙이지 않는다.
- 화물은 계약, 운송 상태, 정산 대상이다. 플레이어가 화물을 직접 집기, 운반, 납품하는 상호작용은 구현하지 않는다.

## 공통 구현 원칙

- 원본 기획서와 충돌하면 원본 기획서와 사용자 확인 사항을 우선한다.
- 새 기능은 순수 규칙을 먼저 Runtime 로직으로 분리하고 EditMode 테스트를 붙인다.
- 씬, 입력, 물리, UI, 카메라, 오디오가 연결되는 기능은 PlayMode smoke를 추가하거나 기존 smoke를 확장한다.
- 빌드 설정, 씬 구성, 패키지, 프로젝트 설정을 바꾸면 Windows 개발 빌드까지 검증한다.
- Steam, 저장, 업적, 클라우드, 온라인 멀티 같은 플랫폼 기능은 인터페이스 뒤에 둔다.
- `Library`, `Temp`, `Logs`, `UserSettings`, `Builds`, `TestResults`는 직접 편집하지 않는다.

## 공통 검증 사다리

각 구현 단계는 변경 범위에 따라 낮은 단계부터 검증한다.

1. `.\scripts\Run-HarnessValidation.ps1`
2. `.\scripts\Run-EditModeTests.ps1`
3. 단계별 smoke 스크립트
4. `.\scripts\Run-PlayModeTests.ps1` 또는 해당 PlayMode smoke
5. `.\scripts\Build-WindowsDev.ps1`

`Run-PlayModeTests.ps1`의 에디터 Test Runner 콜백 타임아웃 문제가 재현되면, 해당 단계의 자동 PlayMode smoke 결과를 필수 증거로 남기고 별도 안정화 항목으로 추적한다.

## 단계별 계획

### 1단계: 상세 구현 기준선 정리

목표: MVP 이후 기능을 안전하게 늘릴 수 있도록 데이터, 테스트, 문서 기준선을 정리한다.

구현 범위:

- 현재 MVP 상태를 Phase 18 기준선으로 고정한다.
- `docs/MVP_PLAYTEST_CHECKLIST.md`를 상세 구현용 회귀 체크리스트로 확장할 구조를 정한다.
- 기획서의 수치가 코드에 이미 존재하는지 확인하고, 중복 상수나 임시 수치 목록을 정리한다.
- 행성, 계약, 화물, 방, 장비, 적대 세력, 위험 구간의 공통 데이터 정의 방향을 확정한다.
- 이후 단계를 고려해 행성, 항로, 계약, 화물, 방, 장비, 적대 세력, 위험 구간의 Runtime 데이터 타입 뼈대를 포함한다.
- 데이터 타입은 Unity `ScriptableObject` 카탈로그보다 순수 C# 데이터와 규칙 모델을 먼저 만들고, 이후 필요할 때 에셋화한다.
- 1단계에서는 타입만 먼저 잡고, 각 타입의 세부 규칙과 동작은 해당 상세 구현 단계에서 채운다.
- PlayMode 전체 테스트 콜백 타임아웃은 1단계에서 반드시 고치고, 재발 여부를 안정화 항목으로 계속 추적한다.

검증:

- Harness validation
- EditMode tests
- Phase18 MVP smoke
- `.\scripts\Run-PlayModeTests.ps1`
- Windows 개발 빌드

완료 기준:

- Phase 18 반복 루프가 기존과 동일하게 통과한다.
- 이후 단계에서 사용할 데이터 카탈로그와 테스트 분류가 문서화된다.
- 이후 단계의 순수 C# Runtime 데이터 타입 뼈대가 생기고 EditMode 테스트가 붙는다.
- `Run-PlayModeTests.ps1`가 결과 XML을 생성하며 안정적으로 종료된다.
- PlayMode Test Runner 안정화 항목이 `docs/PLAYMODE_TEST_RUNNER_STABILITY.md`에 추적 가능하게 남는다.

### 2단계: 행성, 항로, 계약 데이터 모델

목표: 행성 특성, 항로 거리, 계약 유형, 난이도, 보상 산식을 MVP 임시 계약 목록에서 분리한다.

구현 범위:

- 행성 특성 데이터 추가: 물 풍부, 기본 광물 풍부, 유기체 많음, 희귀 광물 풍부, 나무 풍부, 화산 활동 활발.
- 행성은 특성을 하나 이상 가질 수 있게 모델링한다.
- 항로는 출발 행성, 목적지 행성, 운행 시간, 위험 구간 후보, 거리 산식 입력을 가진다.
- 계약 유형을 협회, 개인, 특수로 분리한다.
- 난이도 7단계 추가: 입문, 매우 쉬움, 쉬움, 보통, 어려움, 매우 어려움, 달인.
- 보상 산식 입력을 계약 화물 가치, 거리, 유명세, 협회 유명세, 수리비 지원, 근속 보너스, 협회 유지비로 분리한다.
- 계약 수락 가능 조건에 화물 운송 점수와 창고 상태를 연결한다.

검증:

- 계약 생성과 보상 산식 EditMode tests
- 행성 특성 조합 테스트
- 기존 첫 튜토리얼 계약 회귀 테스트

완료 기준:

- 협회 소속이면 협회 계약이 5개 이상, 비소속이면 2개 이상 노출되는 규칙을 검증한다.
- 계약 보상이 기획서 비율과 정산 문서 기준을 추적 가능하게 계산된다.

### 3단계: 계약 게시판, 유명세, 협회 경제

목표: 플레이어가 다음 운송을 선택할 때 협회 계약, 개인 계약, 특수 계약 후보를 구분해서 판단할 수 있게 한다.

구현 범위:

- 정비 화면의 후속 계약 목록을 계약 게시판 구조로 확장한다.
- 일반 유명세와 협회 유명세를 분리한다.
- 성공, 실패, 사망, 화물 손실, 난이도에 따른 유명세 갱신 규칙을 추가한다.
- 유명세가 낮을 때 개인 계약이 사라지고 협회 계약 수락 시 협회 가입이 강제되는 규칙을 준비한다.
- 유명세가 낮을 때 1회 제공되는 부활 계약 흐름을 추가한다.
- 협회 유지비는 4회차 운송 종료부터 청구되도록 정산 입력에 연결한다.
- 협회 탈퇴 위약금은 데이터와 UI 진입점만 준비하고, 실제 탈퇴 UX는 별도 승인 후 구현한다.

검증:

- 유명세 변동 EditMode tests
- 협회/개인 계약 노출 조건 tests
- 정산 후 계약 게시판 smoke

완료 기준:

- 정산 이후 다음 계약 후보가 유명세, 협회 상태, 화물 운송 점수에 따라 달라진다.
- 협회 경제가 이득과 비용을 모두 드러내며, 정산 결과와 충돌하지 않는다.

### 4단계: 개인 화물과 상점 판매 루프

목표: 개인 화물을 행성에서 수집하고 다른 행성에서 판매하는 보조 수입 루프를 만든다.

구현 범위:

- 개인 화물 데이터 추가: 등급, 크기, 기본 판매가, 출발 행성 특성, 목적지 행성 특성 보정.
- 등급은 평범, 희귀, 특급으로 시작한다.
- 개인 화물 크기는 창고 운송 점수와 적재 가능량에 반영한다.
- 행성 개인 화물 수집소 UI를 정비 화면 안의 진입점으로 추가한다.
- 상점 판매 탭에서 개인 화물만 판매 가능하게 한다.
- 계약 화물은 판매할 수 없고, 직접 납품 상호작용도 만들지 않는다.
- 행성 특성에 따른 판매가 보너스와 디메리트를 적용한다.

검증:

- 개인 화물 적재 가능성 EditMode tests
- 판매가 보정 tests
- 상점 판매 smoke
- Phase18 반복 루프 회귀

완료 기준:

- 개인 화물이 정산과 별개로 상점 판매 수입원이 된다.
- 계약 화물과 개인 화물의 규칙이 UI와 로직에서 명확히 분리된다.

### 5단계: 정비와 화물선 업그레이드 상세

목표: 행성 정비를 단순 수리 화면에서 수리, 업그레이드, 장비 배치의 중심 화면으로 확장한다.

구현 범위:

- 6구역 수리비를 기획서 기준으로 확정한다: 조종실 1%당 30달러, 운송창고 15달러, 동력실 50달러, 통제실 20달러, 무기실 40달러, 비품실 5달러.
- 동력실 0% 견인 비용을 운송 횟수별로 계산한다.
- 화물선 업그레이드 카테고리 추가: 구역 내구도 강화, 포탑/플라즈마, 자동 항법, 비품창고 슬롯, 내부 통제 강화.
- 업그레이드는 구매 상태와 장착 상태를 분리한다.
- 화물선 외형 꾸미기는 데이터와 UI 슬롯만 준비하고, 최종 비주얼 커스터마이징은 아트 패스에서 구현한다.
- 정비 화면에서 다음 운송 위험 요소와 현재 구역 기능 제한을 설명한다.

검증:

- 수리비와 견인비 EditMode tests
- 업그레이드 구매/장착 tests
- 정비 화면 smoke
- Windows 개발 빌드

완료 기준:

- 정비 단계에서 손상, 비용, 업그레이드, 출발 가능 여부가 한 흐름으로 이어진다.
- 기존 Phase10/Phase18 정비 루프가 깨지지 않는다.

### 6단계: 6구역 손상 효과 상세 연동

목표: 원본 기획서의 6구역 손상 단계가 실제 운송, UI, 위험, 침입자 규칙에 영향을 주게 한다.

구현 범위:

- 조종실 손상: 속도 감소, 자동 운행 불가, 방향 전환 입력 지연, 0% 출발 불가와 조종대 폭발.
- 운송창고 손상: 적재 수량 감소, 개인 화물 운송 불가, 화물 손실률, 25% 이하 출발 불가, 0% 지속 손실.
- 무기실 손상: 자동 조준 범위, 포탑 수, 연사 지연, 플라즈마 포 사용 불가, 0% 무기 비활성화와 폭발.
- 동력실 손상: 운송 시간 증가, 암전 구역, 부스터 불가, 구역 기능 off, 0% 견인.
- 통제실 손상: 복도 폐쇄, CCTV 불가, 침입 감지 off, 화물 손상 경고 off, 억제 시스템 off.
- 비품실 손상: 저장 슬롯 감소, 보안 시스템 off, 장비 내구도 하락, 0% 폭발과 장비 폭발 확률.
- HUD와 방 콘솔이 손상 효과를 읽기 쉽게 표시한다.

검증:

- 구역별 threshold EditMode tests
- 운송 중 손상 효과 smoke
- 방 콘솔/CCTV PlayMode smoke

완료 기준:

- 각 구역 손상 단계가 최소 하나 이상의 실제 게임 규칙에 연결된다.
- 임시 수치가 있으면 문서에 명확히 표시되고, 원본 수치가 있는 항목은 원본을 따른다.

### 7단계: 비품창고, 인벤토리, 상점 구매 상세

목표: 플레이어 장비와 비품창고가 전투, 수리, 운송 준비에 필요한 자원 관리 축이 되게 한다.

구현 범위:

- 손에 들 수 있는 아이템 2칸과 주머니 업그레이드 1칸을 정식 모델로 만든다.
- 비품창고 기본 3칸과 업그레이드 슬롯을 구현한다.
- 비품창고 탭 추가: 전체, 무기, 방호, 치료, 강화, 기타.
- 상점 구매 탭을 공통 물품, 유명세 제한 상품, 특별 물품으로 구분한다.
- 상점 구매품을 플레이어 소지품 또는 비품창고에 넣는 규칙을 추가한다.
- 장비 내구도, 버리기, 사용 쿨다운, 판매 시 구매가 1% 처분 규칙을 추가한다.
- 구매 UI는 기능을 먼저 완성하고 최종 디자인은 UX 패스에서 다듬는다.

검증:

- 인벤토리 슬롯과 비품창고 tests
- 상점 구매/보관/처분 tests
- 장비 내구도 tests
- 장비 UI smoke

완료 기준:

- 플레이어가 운송 전 준비한 물품이 운송 중 실제로 접근 가능한 상태로 유지된다.
- 상점 판매 탭의 개인 화물 판매와 구매품 처분 규칙이 충돌하지 않는다.

### 8단계: 무기, 방호, 치료, 강화, 기타 아이템 1차

목표: MVP의 막대기와 머스켓에서 벗어나, 기획서의 핵심 아이템 카테고리를 전투와 생존 루프에 연결한다.

구현 범위:

- 무기 우선순위: 막대기, 머스켓 회귀 안정화 후 샷건, 미니 화염방사기, 전기봉, 단검 순서로 확장한다.
- 방호복과 보호막 관련 기본 방호 아이템을 추가한다.
- 치료 물품: 기본 치료제, 나노머신 치료제 후보 데이터, 사용 시간, 회복량.
- 강화 물품: 급속 보호막 완충제, 수리 장치 후보 데이터.
- 기타 물품: 기척 감지기, 적외선 시야경, 전류 지뢰, 복도 정화 장치의 데이터 껍데기와 잠금 상태.
- 각 아이템은 사용 조건, 사용 결과, 소모 여부, 내구도 감소를 가진다.

검증:

- 무기별 피해량과 사거리 tests
- 방호/치료/강화 효과 tests
- 아이템 사용 입력 smoke
- 침입자 전투 회귀 smoke

완료 기준:

- 모든 아이템 카테고리가 최소 1개 이상 실제 사용 가능한 물품을 가진다.
- 특별 물품은 해금 전 구매 불가 상태로 유지된다.

### 9단계: 플레이어 전투와 상태 이상

목표: 침입자와의 전투가 단순 체력 차감에서 상태 이상, 보호막, 장비 효과를 포함한 생존 판단으로 확장된다.

구현 범위:

- 플레이어 체력과 보호막 피해 적용 순서를 확정한다.
- 상태 이상 추가: 화상, 감전, 출혈, 둔화, 피로, 환각, 공포.
- 상태 이상은 지속 시간, 중첩, 해제 조건, HUD 표시를 가진다.
- 무기와 적 공격이 상태 이상을 부여할 수 있게 한다.
- 방호복과 치료/강화 물품이 상태 이상에 영향을 줄 수 있게 한다.
- 사망자 수, 생존자 0명, 생명 보험 비용, 클리닝 비용 정산과 연결한다.

검증:

- 피해와 보호막 적용 EditMode tests
- 상태 이상 발생/해제 tests
- 전투 PlayMode smoke
- 정산 비용 회귀 tests

완료 기준:

- 플레이어 피해, 사망, 정산 비용이 한 상태 모델로 이어진다.
- 상태 이상이 UI와 전투 결과에 명확히 반영된다.

### 10단계: 조종실, 무기실, 통제실 운용 고도화

목표: 운송 중 플레이어가 어떤 방에 가서 어떤 시스템을 조작할지 결정하는 선택지를 늘린다.

구현 범위:

- 조종실 수동 운행을 위험 구간 회피, 부스터, 자동 운행 전환과 더 긴밀하게 연결한다.
- 부스터 사용 횟수와 동력실 손상 제한을 반영한다.
- 무기실 자동 포탑과 수동 포탑을 분리한다.
- 플라즈마 포 업그레이드, 쿨다운, 우클릭 발사를 추가한다.
- 통제실 CCTV 화면을 구역 상태, 침입자 감지, 화물 상태 경고와 연결한다.
- 세로형 통제 스크린의 임시 폐쇄와 내부 정화 시스템을 1차 구현한다.
- 통제실 손상도에 따라 CCTV와 폐쇄/정화 기능이 제한된다.

검증:

- 조종/부스터 규칙 tests
- 자동/수동 포탑 tests
- 통제실 폐쇄/정화 tests
- 방 운용 PlayMode smoke

완료 기준:

- 조종실, 무기실, 통제실이 서로 다른 대응 수단을 제공한다.
- 구역 손상 상태가 방 운용 기능을 실제로 제한한다.

### 11단계: 외부 위험 구간 확장

목표: 소행성 지대 하나에서 출발한 외부 위험을 기획서의 주요 위험 구간으로 확장한다.

구현 범위:

- 소행성 지대 소형과 대형을 분리한다.
- 자동 조종과 자동 포탑 상태에서 주기적 피격 확률을 적용한다.
- 수동 운행 회피와 수동 포탑 요격을 모두 유효한 대응으로 유지한다.
- 화물 자유 연대 출몰 지역, 우주 해적 출몰 지역, 외계 생명체 출몰 구역의 공통 위험 구간 모델을 추가한다.
- 은폐 블랙홀은 기획서 세부 수치가 부족하므로 데이터 자리와 사용자 확인 항목만 남긴다.
- 위험 구간 발생 확률은 운행 시간, 유명세, 항로, 난이도에 따라 확장 가능하게 한다.

검증:

- 위험 구간 스케줄링 EditMode tests
- 소형/대형 소행성 결과 tests
- 각 위험 구간 대표 smoke

완료 기준:

- 외부 위험이 침입선, 포격, 침입자 발생, 구역 손상 중 하나 이상으로 이어진다.
- 은폐 블랙홀은 구현하지 않고 확인 대기 상태로 문서화한다.

### 12단계: 침입자 AI 공통 프레임워크 완성

목표: 여러 적대 세력을 추가하기 전에 침입자 이동, 목표 선택, 공격, 구역 영향, 세력 관계를 공통화한다.

구현 범위:

- 침입자 목표 유형을 확정한다: 화물 공격, 구역 점유, 플레이어 공격, 화물선 파괴.
- 방과 복도 이동 경로를 침입자 AI가 사용할 수 있게 한다.
- 구역 폐쇄, 암전, CCTV, 억제 시스템이 침입자 이동과 능력치에 영향을 주게 한다.
- 침입자 세력 추가: 씨앗체, 외계 생명체, 화물 자유 연대, 해적.
- 세력 관계를 모델링한다: 적대, 경쟁, 중립, 지휘 관계.
- 침입자 시각 표현은 placeholder에서 시작하되, 식별 가능한 형태와 HUD 신호를 제공한다.

검증:

- 목표 선택 EditMode tests
- 구역 이동과 폐쇄 영향 tests
- 세력 관계 tests
- 침입자 PlayMode smoke

완료 기준:

- 새 침입자 타입을 추가할 때 공통 모델을 재사용할 수 있다.
- Parvum 기존 동작이 공통 프레임워크 위에서 회귀 통과한다.

### 13단계: 씨앗체 상세 구현

목표: Parvum 1종에서 씨앗체 세력의 대표 행동과 화물 재질 상호작용을 확장한다.

구현 범위:

- 우선 구현 순서 제안: Parvum 안정화, Puga, Longa Arma, Tergo, Urgere, Societas, Monstrum, Mimesis.
- Puga는 운송 화물 재질이 필요하므로 2~4단계의 화물 데이터와 연결한다.
- Longa Arma와 Tergo는 사거리, 후방/측면 접근, 구역 공격 차이를 만든다.
- Urgere는 밀어내기, 압박, 이동 방해 규칙을 만든다.
- Societas는 군집 또는 협력 행동을 만든다.
- Monstrum은 대형 위협 또는 특수 목표를 가진다.
- Mimesis는 멀티 음성 흉내 요소가 온라인 구현과 얽히므로, 싱글 플레이에서는 시각/신호 mimic으로 제한한다.
- 씨앗체와 금속 화물, 화물선 구역 피해 규칙을 연결한다.

검증:

- 씨앗체별 데이터 tests
- 대표 행동 tests
- 화물 재질 상호작용 tests
- 씨앗체 침입 smoke

완료 기준:

- 씨앗체는 단순 체력 차이만이 아니라 목표와 대응 방식이 구분된다.
- Mimesis의 온라인 의존 기능은 후순위로 명확히 분리된다.

### 14단계: 외계 생명체 상세 구현

목표: 외계 생명체 출몰 구역과 침입자를 씨앗체와 다른 위협으로 만든다.

구현 범위:

- 외계 생명체 타입 데이터 추가: Cantabile, Con Spirito, Accelerando, Grave, Smorzando, Ostinato, Dolorero.
- 각 타입은 이동 방식, 공격 방식, 상태 이상, 침입 확률, 대응 수단을 가진다.
- 외계 생명체 출몰 구역에서 외부 접근체와 내부 침입자를 연결한다.
- 거대 외계 생물체 회피는 자동 항법 업그레이드 후보로 연결한다.
- 외계 생명체와 해적의 경쟁 관계를 세력 관계 모델에 반영한다.

검증:

- 외계 생명체 타입 rules tests
- 출몰 구역 침입 tests
- 세력 관계 tests
- 대표 외계 생명체 smoke

완료 기준:

- 외계 생명체는 침입 빈도, 상태 이상, 외부 접근 방식에서 씨앗체와 구분된다.
- 모든 타입을 한 번에 완성하지 못하는 경우에도 최소 2종 이상은 실제 위협으로 동작한다.

### 15단계: 화물 자유 연대 상세 구현

목표: 화물 자유 연대를 협회와 세계관적으로 연결된 인간형 또는 기계형 침입 세력으로 구현한다.

구현 범위:

- 화물 자유 연대 출몰 지역과 침입선 접근을 연결한다.
- 침입선 격추 실패 시 구역 손상과 침입자 발생을 적용한다.
- 화물 자유 연대 개체들은 협회, 화물, 플레이어, 구역 시스템에 대한 목표 우선순위를 가진다.
- 레지스탕스, 레볼루션 등 특수 의뢰 드랍 조건과 연결할 대표 개체를 우선 구현한다.
- 화물 자유 연대와 씨앗체, 해적의 적대 관계를 반영한다.

검증:

- 침입선 접근/격추 tests
- 대표 개체 행동 tests
- 특수 의뢰 드랍 조건 tests
- 화물 자유 연대 smoke

완료 기준:

- 화물 자유 연대는 단순 괴물이 아니라 협회 시스템과 연결되는 세력으로 인식된다.
- 특수 의뢰의 선행 조건에 필요한 처치/드랍 이벤트를 제공한다.

### 16단계: 우주 해적 상세 구현

목표: 해적을 고위험 구역, 침입선, 포격, 지휘관 행동으로 구성된 후반 위협으로 만든다.

구현 범위:

- 해적 출몰 구역의 지속 시간, 포격, 침입 확률을 구현한다.
- 해적 침입선 타입과 체력, 탑재 유닛을 데이터화한다.
- 해적 개체 우선순위: 파후르, 쿠르사스, 이슈판트, 아타.
- 아타는 지휘관으로 수호태세와 돌파태세를 지시한다.
- 아타의 구역별 사보타주를 구현한다: 동력 출력 감소, 통제실 해킹, 자동 조종 무력화, 포탑 비활성화, 폭탄 설치.
- 아타 사망 시 해적 개체 정지 규칙을 구현한다.

검증:

- 해적 구역 rules tests
- 포격과 침입선 tests
- 아타 지휘/사보타주 tests
- 해적 침입 smoke

완료 기준:

- 해적은 포격, 침입, 사보타주가 결합된 고위험 세력으로 동작한다.
- 조종실, 통제실, 무기실, 동력실의 상세 구현과 상호작용한다.

### 17단계: 특수 의뢰와 해금 루프

목표: 유명세, 행성 방문, 적 처치, 특정 운송 성공을 장비 해금과 연결한다.

구현 범위:

- 특수 의뢰 조건 모델 추가: 유명세, 행성 특성 방문 횟수, 난이도 완료 횟수, 특정 적 처치 횟수, 특정 아이템 회수.
- 기척 감지기 해금 의뢰를 우선 구현한다.
- 광선검, 전류 지뢰, 복도 정화 장치는 필요한 세력과 아이템 드랍이 구현된 이후 순차 구현한다.
- 특수 의뢰 화물은 자동 정산 성공/실패 흐름과 연결한다.
- 의뢰 실패 시 유명세를 제외한 조건 초기화 규칙을 구현한다.
- 해금된 물품은 상점 또는 정비소에서 구매/장착 가능하게 한다.

검증:

- 특수 의뢰 조건 tests
- 드랍과 회수 tests
- 정산 자동 완료 tests
- 특수 의뢰 smoke

완료 기준:

- 적 처치와 항로 성공이 장비 해금으로 이어진다.
- 특수 의뢰도 직접 납품 상호작용 없이 목적지 도착 정산에서 처리된다.

### 18단계: 행성 내 화면과 UX 완성도

목표: 정비, 계약, 상점, 개인 화물, 업그레이드가 한 행성 체류 흐름으로 자연스럽게 이어지게 한다.

구현 범위:

- 행성 화면에서 정비소, 의뢰소, 상점, 개인 화물 수집소 진입 흐름을 정리한다.
- 행성 맵은 상점, 수리소, 우주선, 화물 공급소를 표시한다.
- 계약 게시판은 협회, 개인, 특수 계약을 구분해서 보여준다.
- 상점은 구매 탭과 판매 탭을 명확히 분리한다.
- 정비 화면은 수리, 업그레이드, 배치, 출발 가능 여부를 통합해서 보여준다.
- 튜토리얼 이후 스킵 버튼과 1000달러 지급 조건을 재검토한다.
- 협회 계약서의 자동 스크롤, Ctrl+C, Ctrl+X 개인 사업자 루트는 사용자 재확인 후 구현한다.

검증:

- 행성 화면 PlayMode smoke
- 계약/상점/정비 UI 회귀 smoke
- 텍스트 겹침과 버튼 상태 수동 체크리스트

완료 기준:

- 운송 종료 후 다음 운송 준비까지 필요한 주요 행동이 행성 화면에서 모두 가능하다.
- 구현이 확정되지 않은 히든 루트는 사용자 승인 전 구현하지 않는다.

### 19단계: 저장, 설정, 플랫폼 경계

목표: 상세 구현된 게임 상태를 세션 간 유지하고, Steam 출시 준비를 위한 경계를 단단하게 만든다.

구현 범위:

- 저장 대상 정의: 플레이어 장비, 비품창고, 화물선 상태, 업그레이드, 유명세, 협회 상태, 특수 의뢰 진행도, 방문 행성 기록.
- 튜토리얼 완료 여부와 스킵 가능 여부를 저장한다.
- 설정 대상 정의: 해상도, 음량, 마우스 감도, 키 설정 후보.
- 업적, 클라우드, Steam 통계는 인터페이스만 준비하고 실제 SDK 연결은 하지 않는다.
- 저장 파일 버전과 마이그레이션 정책을 둔다.

검증:

- 저장/로드 EditMode tests
- 버전 마이그레이션 tests
- 새 게임과 이어하기 smoke
- Windows 개발 빌드

완료 기준:

- 플레이테스트 중 반복 진행한 결과가 안전하게 저장되고 복구된다.
- Steam 기능을 붙이기 전에도 게임 로직은 플랫폼 SDK를 직접 참조하지 않는다.

### 20단계: 아트, 사운드, 연출, 레벨 완성도

목표: graybox와 placeholder를 플레이 가능한 품질로 끌어올리되, 기능 안정성을 해치지 않게 단계적으로 교체한다.

구현 범위:

- 6구역과 복도 구조를 기획서 묘사에 맞춰 정리한다.
- 조종실 전면 유리, 동력실 도넛형 구조, 통제실 스크린 구성, 무기실 포탑 자리, 비품실 창고와 사출대, 운송창고 중심 화물 표현을 다듬는다.
- 저채도, 어두운 조명, 제한 시야, 위험 신호 사운드를 상세화한다.
- HUD 체력/보호막, 맵, 침입 신호, 구역 경고 연출을 다듬는다.
- 적대 개체 placeholder를 타입별 식별 가능한 모델 또는 임시 고품질 표현으로 교체한다.
- 성능 예산과 로딩 시간을 측정한다.

검증:

- 주요 씬 PlayMode smoke
- 시야, UI 겹침, 카메라 클립 수동 체크
- 성능 샘플링
- Windows 개발 빌드

완료 기준:

- 주요 방과 적대 타입이 플레이 중 식별 가능하다.
- 연출 추가 후에도 Phase18 루프와 최신 단계 smoke가 통과한다.

### 21단계: 밸런싱과 플레이테스트 하드닝

목표: 상세 구현된 싱글 플레이 루프를 반복 테스트 가능한 출시 후보 수준으로 안정화한다.

구현 범위:

- 계약 보상, 수리비, 위험 발생 확률, 침입자 체력과 피해량, 아이템 가격을 조정한다.
- 난이도별 위험과 보상이 증가하는지 확인한다.
- 초반 30분, 중반 반복 운송, 고위험 특수 의뢰 시나리오를 플레이테스트 항목으로 만든다.
- 실패 후 복구 가능성, 게임 오버 조건, 부채 유예 규칙을 재검증한다.
- 자동화 smoke를 최신 핵심 루프 기준으로 통합하거나 단계별로 유지할지 결정한다.
- 플레이테스트 버그를 우선순위별로 triage한다.

검증:

- Harness validation
- EditMode tests
- 전체 핵심 smoke 묶음
- Windows 개발 빌드
- 수동 플레이테스트 체크리스트

완료 기준:

- MVP 루프가 상세 시스템을 포함한 상태에서도 반복 가능하다.
- 온라인/멀티 구현에 들어가기 전에 싱글 플레이와 로컬 상태 경계가 안정적이라는 근거가 남는다.

### 22단계: 온라인/멀티플레이 설계 게이트

목표: 최대 5인 온라인 멀티 구현을 시작하기 전에 권한 모델, 동기화 범위, Steam 연동 범위를 별도 설계한다.

구현 범위:

- 이 단계는 구현 단계가 아니라 설계 승인 단계다.
- 최대 5인 파티의 host authority 모델을 정의한다.
- 조종실, 무기실, 통제실, 비품창고, 정비/상점/계약 UI의 상호작용 소유권을 정한다.
- 위험 구간, 침입자, 정산, 사망자 수, 화물 손실, 방 손상은 authoritative session에서만 확정되게 한다.
- Steam lobby, invite, reconnect, late join, disconnect, migration 여부를 결정한다.
- 로컬 협동 상태 모델을 어떤 온라인 메시지로 매핑할지 결정한다.
- 네트워크 테스트 전략과 headless 또는 multi-instance 검증 방식을 정한다.

검증:

- 문서 리뷰
- 로컬 협동 foundation 회귀
- 네트워크 구현 전 위험 분석 체크리스트

완료 기준:

- 사용자가 온라인/멀티 설계를 별도로 승인한다.
- 승인 전에는 Steam 로비, 실제 네트워크 패키지, 최대 5인 동기화 구현을 시작하지 않는다.

## 사용자 확인 필요 항목

아래 항목은 구현 전에 사용자 확인이 필요하다.

- 씨앗체 세부 구현 순서가 `Parvum -> Puga -> Longa Arma -> Tergo -> Urgere -> Societas -> Monstrum -> Mimesis`가 맞는지.
- 무기 확장 순서가 `샷건 -> 미니 화염방사기 -> 전기봉 -> 단검`이 맞는지.
- 은폐 블랙홀을 상세 구현 단계 안에 넣을지, 후반 확장으로 미룰지.
- 협회 계약서의 Ctrl+C/Ctrl+X 개인 사업자 루트를 언제 구현할지.
- 화물선 외형 꾸미기를 기능 중심 placeholder로 먼저 둘지, 아트 패스에서 본격 구현할지.
- 모든 적대 타입을 완성한 뒤 특수 의뢰를 구현할지, 필요한 대표 타입만 먼저 만들고 특수 의뢰를 병행할지.

## 승인 후 첫 작업 후보

승인 후 첫 구현 후보는 1단계다. 1단계에서는 새 게임 기능을 늘리기보다, 2단계 이후의 데이터 모델과 검증 루프가 흔들리지 않도록 현재 MVP 기준선을 정리한다.

구현 시작 전 확인할 것:

1. 이 문서의 단계 순서를 그대로 채택할지.
2. 1단계 범위는 기준선 정리, 순수 C# Runtime 데이터 타입 뼈대, PlayMode Test Runner 타임아웃 수정까지 포함한다.
3. 온라인/멀티는 22단계 설계 게이트 전까지 구현하지 않는다.
